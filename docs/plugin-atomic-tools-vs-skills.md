# 架构边界：插件 = 原子工具，工作流 = 技能 + 记忆

> 本文档说明 dsh-matrix-agent 的职责边界，以及「工作目录如何确定」「秘书如何与主人协商」
> 这类**可定制策略**应该落在哪一层。

## 核心原则

- **插件（dsh-matrix-agent）**：只提供**原子的、可组合的最小动作**（原子工具），不做
  「岗位→目录」「角色→行为」这类策略判断。
- **技能（skill）**：定义「每个员工的工作流」——用 `SKILL.md` 组合原子工具，每个真实
  员工把它放进 `<dshHome>/skills/` 即可定制自己的行为。
- **记忆（memory）**：插件持久化「工作内容 → 目录」等经验（`matterCwds`），让秘书对
  同类工作形成记忆，下次自动建议，无需技能层重复设定。

## 为什么这样分

每个真实员工的岗位不同（综合研发、产品、领导…），且**每个员工跑一个独立 dsh 进程**，
工作目录由「这个人的工作内容」决定，而不是由「角色名」硬编码。把这些差异放进插件代码
会让插件无限膨胀；放进技能/记忆则让每个员工自己定制、自己沉淀。

## 插件提供的原子工具（模型可调）

| 工具 | 作用 | 属于哪一层 |
|---|---|---|
| `matrix_set_room_cwd` | 把会话绑定到工作目录（绝对路径） | 原子动作 |
| `matrix_request_owner_decision` | 私下向主人请示（自动补群名/发起人/内容） | 原子动作 |
| `matrix_report_owner` | 私下向主人汇报进度/结果 | 原子动作 |
| `matrix_get_room_members` / `matrix_get_recent_messages` / … | 感知群上下文 | 原子动作 |
| `matrix_send_room_message` / `matrix_send_dm` / `matrix_mention_member` | 对外/对主人发消息 | 原子动作 |
| `twin_timeline` | 查自我跨房间历史 | 记忆查询 |

## 技能如何组合（示例）

见 `skills/product-manager-workflow/SKILL.md` 和 `skills/rnd-engineer-workflow/SKILL.md`。
核心是：**技能里写「工作目录规则」和「请示/汇报规则」**，用自然语言指导数字人何时调用
哪个原子工具，而插件只保证工具本身可靠。

## 隐私红线（插件内置，不依赖技能）

无论技能怎么写，插件保证：

- 有 owner（数字分身）时，群里**绝不出现**「待审/请示中/待确认/老板」等甩锅文案，
  只显示中性进度（「收到，我来处理」「进行中」「已完成」）。
- 请示/汇报**只通过私聊（DM）**送达主人，且正文自动补全「哪个群、谁安排的、什么工作、
  建议目录」。

## 目录解析优先级

主人显式答复目录 > 秘书经验记忆（`matterCwds`）> `workspaceRegistry`/`cwdCandidates`
首项 > `process.cwd()`。前三者经请示 DM 由主人拍板。
